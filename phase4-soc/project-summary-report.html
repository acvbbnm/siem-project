1. 프로젝트 개요

1-1. 목적 및 범위

본 프로젝트는 통합보안관제(SOC) 가상환경에서 공격 수행 → 탐지/분석 → 관제 대응까지 전체 사이클을 실습하고 기록하는 방어 보안(교육용) 프로젝트이다.

핵심 목표: 격리된 실습 랩에서 실제 공격 도구(nmap, hydra, sqlmap, wpscan)를 사용하여 킬체인 공격을 수행하고, Snort IDS + ModSecurity WAF + Splunk SIEM 기반 탐지·대응 체계의 효과를 검증한다.

프로젝트 구성 (4+1 Phase):

Phase내용기간
Phase 1Bee-box(bWAPP) 대상 기본 공격 수행 — 정찰, SQLi, XSS, 명령주입, 브루트포스8/3~8/10
Phase 2Snort IDS 탐지 분석 + pfSense 방화벽 정책 수립8/10~8/11
Phase 2.5실제 운영 환경 확장 구축 — WordPress, ModSecurity, MySQL, rsyslog8/18~8/25
Phase 3WordPress 킬체인 7단계 공격 + 커스텀 탐지 룰 구축8/25~8/26
Phase 4SOC 관제 운영 — 대시보드, Alert, 관제 일지, 최종 보고서8/27

2. 환경 구성

2-1. 초기 환경 (Phase 1~2)

초기 환경은 att-mint(공격자) → pfSense(방화벽+Snort) → Bee-box(취약 웹서버)의 단순 구조였다. 공격자가 pfSense NAT를 통해 DMZ의 Bee-box(bWAPP)에 접근하고, Snort가 네트워크 트래픽을 모니터링하는 구조이다.

Phase 1에서 Bee-box 대상 기본 공격(정찰, SQLi, XSS, 명령주입, 브루트포스)을 수행하고 Phase 2에서 Snort 탐지 분석 및 방화벽 정책을 수립하였다.

[그림 2-1] VirtualBox VM 구성 화면
VirtualBox Manager 화면 — 실습에 사용된 전체 VM 목록(att-mint, Kali, VyOS, pfSense, Bee-box, WordPress, MySQL, Splunk, mng-mint)과 각 VM의 설정 상태가 보이는 스크린샷
[그림 2-2] 네트워크 토폴로지 다이어그램
전체 네트워크 구성도 — att-net(10.50.50.0/24), rf-net, dmz-net(10.0.10.0/24), inner-net(10.0.100.0/24), mng-net(10.0.50.0/24) 대역과 VyOS·pfSense를 중심으로 한 라우팅/NAT 구조를 보여주는 다이어그램 또는 화이트보드 캡처
[그림 2-3] pfSense WAN 방화벽 룰

2-2. 환경 확장 (Phase 2.5) — 왜 확장했는가

초기 환경에서 Bee-box는 의도적으로 취약하게 설계된 학습용 서버로, 실제 운영 환경과 큰 차이가 있었다. 실무 SOC 관제 능력을 기르기 위해 다음과 같이 환경을 확장하였다:

3. 공격 수행

3-1. Phase 1: Bee-box 기본 공격

Phase 1에서는 att-mint(10.50.50.17)에서 pfSense NAT를 통해 Bee-box(bWAPP)를 대상으로 정찰 4단계 + 공격 7종을 수행하였다.

정찰 (Reconnaissance)

정찰은 넓게 → 좁게(포트 → 버전 → 웹설정 → 숨은경로) 순서로 공격 지도를 완성하는 과정이다.

4. 탐지 엔지니어링

4-1. Snort IDS 커스텀 룰

pfSense의 Snort에 기본 룰셋(GPLv2 + ET Open) 외에 WordPress 공격 탐지를 위한 커스텀 룰 9개를 추가하였다.

실무 확장 — 동일 경보가 오탐이 되는 상황

본 실습은 통제된 환경에서 의도적 공격을 수행했기 때문에 모든 경보가 정탐으로 판정되었다. 그러나 실무 SOC에서는 동일한 경보 유형이라도 상황에 따라 오탐으로 판정되는 경우가 존재한다. 분석가는 아래와 같은 오탐 시나리오를 인지하고, 위 4단계 프로세스를 통해 구분할 수 있어야 한다.

경보 유형오탐 시나리오 (실무)판별 포인트
Scanner Detection자사 보안팀이 운영하는 취약점 스캐너(Qualys, Nessus, Acunetix)가 정기 점검 수행 시 User-Agent에 "scanner" 포함1단계에서 출발지 IP가 보안팀 자산 목록에 등록되어 있는지 확인. 스캔 일정표와 대조
Brute Force사내 비밀번호 변경 정책 적용일에 다수 직원이 이전 비밀번호로 로그인 실패. 또는 SSO/LDAP 연동 오류로 인증 실패 반복2단계에서 요청 간격이 사람 속도(수 초)인지, 자동화 속도(밀리초)인지 구분. 다수 IP에서 분산 실패인지, 단일 IP 집중인지 확인
SQL InjectionCMS 게시판에 프로그래밍 관련 글 작성 시 "SELECT", "UNION" 등 SQL 예약어가 본문에 포함3단계에서 해당 문자열이 HTTP 파라미터(공격)인지, POST 본문 콘텐츠(정상 글)인지 위치 확인. 요청 경로가 게시판(/wp-comments-post.php)인지 취약 엔드포인트인지 구분
WAF Anomaly ScoreAPI 클라이언트나 모바일 앱이 비표준 User-Agent 사용, 또는 대용량 파일 업로드 시 CRS 룰에 의해 anomaly score 누적2단계에서 User-Agent가 자사 앱의 알려진 UA인지 확인. 요청 빈도와 패턴이 정상 API 호출 주기와 일치하는지 대조
Webshell (cmd=)웹 애플리케이션이 정상적으로 cmd 파라미터를 사용하는 경우 (검색 필터, 명령어 도움말 페이지 등)3단계에서 cmd 값이 시스템 명령(id, whoami, cat)인지, 애플리케이션 정상 값(search, filter)인지 페이로드 내용 확인. 4단계에서 응답에 시스템 정보 노출 여부 확인
핵심 인사이트: 정탐/오탐 판별의 본질은 "경보가 울렸다/안 울렸다"가 아니라, "경보가 울린 이유를 역추적하여 공격 의도(Intent)와 공격 성공 여부(Impact)를 확인하는 분석 과정"이다. 동일한 시그니처라도 출발지·행위·페이로드·영향도의 조합에 따라 판정이 달라지며, 이 프로세스를 체계적으로 수행하는 것이 SOC 분석가의 핵심 역량이다.

부분 탐지 심층 분석 — DB 접근 탐지 불가의 구조적 원인

웹쉘(hello.php)을 통한 DB 접근이 탐지되지 않은 결정적 원인은 권한 및 세션의 동질성이다.

웹쉘은 Apache 웹 서버 프로세스 권한(www-data) 위에서 동작하며, DB 접근 시에도 정상 WordPress 소스코드와 동일한 wp-config.php 내부의 평문 인증정보(wp_admin / WpAdmin!2024)를 그대로 도용한다. 결과적으로 MySQL 서버 입장에서는 정상 웹 애플리케이션의 쿼리와 웹쉘 경유 쿼리가 동일한 출발지 IP(10.0.10.80), 동일한 계정(wp_admin), 동일한 커넥션 경로로 인입되어, 네트워크 및 DB 커넥션 레벨에서 악성 행위를 식별하는 것이 불가능하였다.

구조적 개선 제언

구분개선 방안상세
감사 로그 고도화MySQL Audit Plugin 활성화단순 커넥션 로깅이 아닌 실행된 SQL 쿼리 패턴을 기록. 평소 웹 애플리케이션이 수행하지 않는 테이블 전체 dump(SELECT * FROM wp_users) 패턴을 SIEM에서 행위 기반으로 탐지
시스템 레벨 제어php.ini disable_functions 설정system(), exec(), passthru(), shell_exec() 등 위험 함수를 비활성화하여 웹쉘이 OS 명령(CLI 형태의 mysql 직접 실행)을 수행하는 경로를 원천 봉쇄
DB 접근 분리애플리케이션 전용 DB 계정 세분화WordPress용 DB 계정의 권한을 최소화(필요 테이블 SELECT/INSERT/UPDATE만 허용)하고, wp_users 전체 조회 권한을 제거하여 웹쉘이 도용하더라도 민감 데이터 접근 차단

왜 현재 도구로는 탐지할 수 없는가

현재 구축된 탐지 체계(Snort IDS, Splunk SIEM, ModSecurity WAF)는 모두 네트워크 트래픽 및 애플리케이션 로그 레벨에서 동작한다. 그런데 웹쉘을 통한 DB 접근은 다음과 같은 이유로 이 레벨에서 정상 트래픽과 구별이 불가능하다.

탐지 도구관찰 가능 범위웹쉘 DB 접근이 탐지 불가한 이유
Snort IDS네트워크 패킷 (L3~L7)WordPress ↔ MySQL 간 3306 트래픽은 정상이든 웹쉘이든 동일한 출발지(10.0.10.80), 동일한 포트, 동일한 프로토콜. Snort 룰로 쿼리 내용 구분하려면 MySQL 프로토콜 디코딩이 필요하나, 비표준이며 암호화 시 불가
Splunk SIEM수집된 로그 (Apache, pfSense 등)Apache access.log에는 /?cmd=mysql... 형태로 요청이 기록되나, DB 쿼리 결과나 접근 성공 여부는 기록되지 않음. MySQL 로그가 미수집 상태
ModSecurity WAFHTTP 요청/응답 (L7)WAF는 HTTP 레이어만 검사. 웹쉘이 서버 내부에서 DB에 접근하는 행위는 HTTP 요청이 아니므로 WAF 관찰 범위 밖
핵심 — 관찰 지점의 한계
모든 현재 도구는 "네트워크를 지나가는 트래픽"을 본다. 그러나 웹쉘→DB 접근은 서버 내부에서 발생하는 프로세스 실행이므로, 네트워크 관찰로는 원천적으로 탐지 불가능하다. 이것이 엔드포인트 레벨 탐지(EDR)가 필요한 근본적 이유이다.

EDR이 탐지할 수 있는 이유 — 프로세스 체인 분석

EDR(Endpoint Detection and Response)은 서버 엔드포인트에서 프로세스 실행을 실시간 모니터링한다. 정상 WordPress와 웹쉘의 DB 접근은 프로세스 트리 구조가 완전히 다르며, EDR은 이 차이를 탐지한다.

정상 WordPress DB 접근웹쉘 경유 DB 접근
프로세스 체인 apache2 → php-fpm → mysqli_query()
(인프로세스 라이브러리 호출, 자식 프로세스 없음)		 apache2 → php-fpm → system() → /bin/sh → mysql CLI
(자식 프로세스 생성 = 비정상)
실행 방식 PHP의 mysqli 확장으로 DB 드라이버를 라이브러리로 직접 호출 — 별도 프로세스 생성 없음 system("mysql -u wp_admin -p... -e 'SELECT * FROM wp_users'")로 외부 CLI 프로그램을 실행
EDR 관점 apache2 자식으로 php-fpm만 존재 → 정상 프로세스 트리 php-fpm이 /bin/sh를 spawn → 비정상 프로세스 트리 경보
EDR 탐지 룰 예시
parent_process = "php-fpm" AND child_process IN ("sh", "bash", "mysql", "mysqldump")
→ 웹 서버 프로세스가 쉘이나 DB CLI를 자식으로 생성하면 즉시 경보. 정상 WordPress 운영에서는 절대 발생하지 않는 패턴이므로 오탐률이 매우 낮다.

8-3. EDR 연계 및 AI 활용 방향

EDR 연계

현재 환경에는 EDR이 없다. EDR을 연계하면 네트워크(Snort/WAF) + 엔드포인트(프로세스 트리, 파일 변경, 메모리 분석)를 통합하여 더 정밀한 탐지가 가능하다.

[현재 — 네트워크만]
  Apache 로그에서 /?cmd= 탐지 → 수동으로 웹쉘 확인

[EDR 연계 시]
  www-data → shell_exec() → mysql 자식 프로세스 → hello.php 변경 자동 탐지 → 엔드포인트 자동 격리

AI 활용

  • 이벤트 자동 분류: 대량 경보 중 정탐/오탐 AI 1차 분류 → 분석가는 "확인 필요"에만 집중
  • IP 평판 자동 조회: VirusTotal/AbuseIPDB 자동 연동 → 컨텍스트가 붙은 경보 제공
  • 킬체인 패턴 인식: 정찰 → 브루트포스 → 웹쉘 순서를 인식하여 조기 경보
  • 대응 자동화: 방화벽 룰 추가, EDR 격리 등을 AI가 제안 → 분석가 승인
이 프로젝트의 의미: "공격 시뮬레이션 → 탐지 → 분석 → 대응" 사이클은 실제 SOC Tier 1 업무의 축소판이다. 인프라 구축부터 공격자 관점의 킬체인 수행, 방어자 관점의 탐지 룰 설계, 그리고 관제 대응까지 전체 흐름을 경험함으로써 SOC 분석가의 핵심 역량인 "왜 이 경보가 떴는가? 정탐인가? 다음은 무엇인가?"의 분석적 사고를 체득하였다.

A-2. Splunk 쿼리 모음

대시보드 쿼리

# 전체 이벤트 수
index=pfsense OR index=idx_web OR index=idx_waf OR index=idx_db | stats count

# 공격자 IP Top5
index=pfsense "Priority"
| rex "\{(?P<proto>\w+)\}\s+(?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| top 5 src_ip

# 공격 유형 분포
index=pfsense "Priority"
| rex "\[\d+:\d+:\d+\]\s+(?P<signature>[^\[]+?)\s+\["
| top 10 signature

# 로그인 시도 IP별
index=idx_web "wp-login"
| rex "client\s+(?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count by src_ip

Alert 쿼리

# Brute Force Detection (Critical, */5분)
index=idx_web "wp-login.php" "POST" | stats count | where count >= 10

# SQL Injection Detection (Critical, */5분)
index=pfsense ("SQL" OR "1000004") "Priority" | stats count | where count >= 2

# Webshell Detection (Critical, */5분)
index=idx_web "cmd=" | stats count | where count >= 1

# WAF Alert Surge (Medium, */10분)
index=idx_web "ModSecurity" | stats count | where count >= 30

실무 관점 쿼리 리뷰 및 개선 방향

공격자 IP Top5 쿼리 — rex 성능 이슈
현 상태: rex 명령어로 정규표현식을 사용해 매 검색 시 src_ip를 실시간 추출하고 있다.
실무 피드백: 대량 로그가 인입되는 상용 환경에서 rex는 검색 시점마다 CPU를 소모하는 Search-Time Extraction이므로 심각한 성능 오버헤드를 유발한다. Snort 연동 시 Splunk 앱 또는 transforms.conf에서 src_ip 필드가 인덱싱 단계에서 자동 추출(Index-Time Field Extraction)되도록 전처리 설정을 해두고, 쿼리는 | top limit=5 src_ip와 같이 단순 통계 함수만 사용하여 인덱싱 성능을 최적화해야 한다.
Brute Force Detection 쿼리 — 공동 오탐(False Positive) 리스크
현 상태: stats count로 전체 POST 요청 수만 집계하고 있어, IP 구분 없이 총합이 임계치(10건)를 넘으면 트리거된다.
실무 피드백: 이 구조에서는 서로 다른 10명의 정상 사용자가 각각 1회 로그인 실패해도 경보가 발생하는 공동 오탐의 리스크가 있다. 반드시 stats count by src_ip 구문을 추가하여 "특정 단일 IP"에서 임계치 이상 실패가 발생했을 때만 트리거되도록 그룹화해야 한다.
